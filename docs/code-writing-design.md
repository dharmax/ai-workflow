# Canonical code writing — design

**Status:** authoritative design for AIWF-generated repository source. Planning only; current `resolve_ticket` still uses direct LLM synthesis / implementation Actor paths until this design is implemented and accepted.

**Prime Directive:** the simplest correct solution wins. Reuse text-compiler, skill-manager, the existing Causal Change Engine, ToolContext authority, TestNodes and artifact operations. Do not add a second editor, compiler, workflow engine, registry, planner or safety system.

---

## 1. Actor journey first

### J3.4 — turn grounded implementation intent into verified source

A Ticket resolver or general coding Actor has already established a concrete implementation outcome and enough repository evidence to identify an exact source target. It needs new or replacement source code, not another round of repository navigation.

AIWF activates concise software-implementation know-how, asks one canonical code-writing capability for the smallest source change that satisfies the grounded intent, applies that change only through the existing Causal Change Engine, runs the relevant project verification, and feeds observed failures back through the same writing capability for bounded repair.

If the target is still ambiguous, AIWF returns to investigation/navigation instead of asking the writer to guess. If the requested mutation is deterministic — rename, organize imports, existing language-server refactor — AIWF uses the deterministic change primitive directly rather than invoking generative synthesis.

The observable end state is either:

- the intended source change exists, project verification and authored acceptance pass, and evidence is reusable; or
- AIWF reports the concrete unresolved target, synthesis, mutation, test, authorization or acceptance blocker.

The external coding agent never has to manufacture replacement source or reproduce AIWF's implementation workflow manually.

---

## 2. Architectural correction

Today AIWF has multiple source-producing paths:

- direct `asker.json(... ExactImplementationSchema ...)` for one exact symbol;
- an implementation `LLMActor` that can place replacement source directly into `preview_change/apply_change`;
- low-level `compile_codelet` that asks the Actor itself to supply source;
- text-compiler as a separate sibling capable of code synthesis/repair.

That is duplicate responsibility.

### New invariant

> **All nontrivial source text generated by AIWF for repository implementation goes through one canonical `write_code` capability backed by text-compiler.**

This does **not** mean every code mutation uses an LLM.

Deterministic operations remain deterministic:

- rename symbol/file;
- language-server refactors;
- organize/fix imports where a deterministic source action exists;
- exact user-authored patches;
- other existing Causal Change Engine operations that do not require AIWF to invent source.

The invariant is about **AIWF-authored new/replacement source**, not all filesystem mutation.

## 3. Responsibility boundaries

```text
Actor / Ticket.resolve
        |
        | decides what outcome/target is needed
        | obtains repository evidence
        v
software-implementation skill
        |
        | reusable engineering know-how / procedure
        v
write_code capability
        |
        | source synthesis only for a grounded exact target
        v
@dharmax/text-compiler
        |
        | text -> candidate source + bounded synthesis diagnostics
        v
CausalChangeEngine
        |
        | preview / fingerprint / safe apply / structural verification
        v
project tests + TestNodes + acceptance verifier
        |
        v
verified Ticket / observed blocker
```

### Actor / resolver owns

- goal and Ticket acceptance;
- navigation and exact target selection;
- Product Intent / Aspect / Decision / Lesson constraints;
- deciding when a deterministic refactor is preferable;
- deciding whether another target/change is needed;
- tests, repair loop and final acceptance.

### Skill owns

Reusable know-how: how AIWF expects software implementation to be approached.

It is guidance, not authority and not an executor.

### `write_code` owns

- translating a **grounded, bounded implementation intent** into source for an exact target;
- loading the current target source itself rather than trusting stale model-provided source;
- passing exact source/context + constraints to text-compiler;
- converting the candidate into the appropriate existing `CodeChangeRequest`;
- previewing/applying through the Causal Change Engine under caller authority;
- returning explicit synthesis/mutation provenance.

It does **not** discover arbitrary targets, run the whole Ticket lifecycle, create Product Intent, or own project test acceptance.

### text-compiler owns

Code synthesis, bounded critique/repair and compiler-specific diagnostics.

It does **not** know Tickets, Semantika entities, leases, Git dirty state, Product Intent or repository mutation.

### Causal Change Engine owns

Repository mutation correctness: target resolution, preview fingerprint, safe apply, reindex/diagnostics and structural verification.

It does not generate implementation source.

## 4. The built-in software-implementation skill

Add a built-in instructional skill, loaded through `@dharmax/skill-manager`, not hard-coded as another giant Actor prompt.

Suggested identity: `software-implementation`.

It should be concise and AIWF-specific. The base model already knows general programming. Do **not** turn the skill into a programming textbook.

Normative content:

1. Start from the accepted actor/Ticket outcome and exact acceptance criteria.
2. Inspect the actual target and nearby conventions before synthesis.
3. Preserve architecture, accepted Decisions, Lessons, Aspects and project instructions.
4. Prefer the smallest correct change and existing abstractions.
5. Prefer deterministic language/refactor operations when no source invention is required.
6. When new/replacement source is required, use the canonical `write_code` capability; do not hand-author replacement source in generic change tools.
7. Do not weaken tests or acceptance to make a change pass.
8. Treat compiler/change/test failures as observations; repair the underlying implementation through the same canonical path.
9. Verify project behavior after mutation; generated compiler examples/tests are not project acceptance evidence.
10. Stop on genuine target/product ambiguity rather than guessing.

The skill may declare the canonical writer capability as a requirement once the runtime capability ID is established. Do not invent a second capability resolver merely for this declaration.

### Guidance precedence

Hard enforcement remains outside the skill:

```text
ToolContext / ChangeEngine / lease / dirty-target / acceptance invariants
    > authored implementation constraints considered together:
        explicit user + Ticket contract
        accepted Decisions / Aspects / Lessons / Product Intent
        project AGENTS/repository instructions
      (material conflict => needs_input / explicit decision; do not silently choose)
    > built-in software-implementation skill
    > generic model knowledge
```

A missing skill may reduce quality but must not disable hard safety or create an unsafe fallback.

## 5. Canonical `write_code` capability

### Scope

First version intentionally supports bounded source generation where the target is already concrete:

- replace an exact function/method/class/interface/symbol;
- replace an exact bounded source range/block in a known source file (for example an import/declaration block) using fresh old text read by AIWF;
- create a new source file with an explicit path and bounded purpose.

Do not make the first version a repository-wide autonomous coding service. Multi-file work is composed by the resolver/Actor from multiple grounded writes plus deterministic refactors.

### Conceptual input

```ts
interface WriteCodeRequest {
  intent: string
  target:
    | { kind: 'symbol'; filePath: string; symbolName: string; containerName?: string }
    | { kind: 'range'; filePath: string; startLine: number; startCharacter: number; endLine: number; endCharacter: number }
    | { kind: 'new-file'; filePath: string }

  acceptance?: string[]
  constraints?: string[]
  guidance?: string
  feedback?: string[]
  productContextEntityId?: string
}
```

The exact public schema may use existing `ChangeTarget` shapes where possible; do not duplicate target types.

### Preconditions

- project-write authority for mutation;
- exact existing symbol, exact bounded source range, or explicit new-file path;
- caller-provided implementation intent grounded in Ticket/user goal;
- no unowned dirty target unless already authorized by existing resolver rules.

`write_code` must reuse the current dirty-target protection mechanically. If that logic is only inline in Ticket.resolve, extract the smallest shared guard and reuse it; do not duplicate a safety subsystem. Ticket.resolve remains the lease owner for Ticket work — the writer must not create a second leasing lifecycle.

If target discovery is still needed, return a precise target-needed result. Do not make `write_code` perform broad semantic search.

### Execution

For an existing symbol:

1. Resolve/read exact current symbol source and enough bounded surrounding context.
2. Gather applicable project doctrine supplied by the caller/skill and relevant authored constraints.
3. Ask text-compiler for a replacement source fragment.
4. Validate that the result is nonempty and compatible with the intended target shape.
5. Construct existing `replace_symbol` request.
6. Preview through CausalChangeEngine.
7. Apply through CausalChangeEngine under existing authority/dirty-target/lease rules.
8. Return applied change + synthesis metadata.

For an exact source range/block:

1. Read the fresh bounded old text from the source file.
2. Gather only the surrounding context required to preserve syntax/conventions.
3. Ask text-compiler for replacement source for that exact region.
4. Construct existing `replace_text` using the freshly observed old text; never ask the Actor to provide the old anchor.
5. Preview/apply through CausalChangeEngine.
6. Return applied change + synthesis metadata.

For a new file:

1. Confirm target does not already exist.
2. Gather bounded neighboring/module conventions.
3. Ask text-compiler for complete file source.
4. Construct existing `create_file` request.
5. Preview/apply through CausalChangeEngine.
6. Return applied change + synthesis metadata.

### Result

Return enough truth for the resolver/Actor to continue, for example:

```ts
{
  applied: boolean
  target: ...
  filesTouched: string[]
  changeFingerprint: string
  sourceHash: string
  compiler: {
    kind: 'text-compiler'
    diagnostics?: ...
    attempts?: number
  }
  verification: ChangeApplyResult['verification']
}
```

Do not persist generated source in aggregate metrics or a parallel codelet store. Existing source control + ChangeEngine result + verification receipt are the durable truth.

## 6. text-compiler integration: do not misuse codelets

Current `compileCodelet()` is designed to produce an executable function/codelet. A repository method declaration, class member, interface or module is a different artifact shape.

Do **not** coerce every repository edit into an executable codelet merely to say text-compiler was used.

### Minimal sibling extension

Add a narrow source-synthesis API to text-compiler if the Phase-0 audit confirms no equivalent public API already exists.

Conceptually:

```ts
compiler.compileSource(intent, {
  language,
  form,              // symbol/declaration/module, small closed vocabulary
  existingSource?,
  surroundingContext?,
  constraints?,
  feedback?,
  useCritic?,
  recovery?
}) -> {
  sourceCode,
  diagnostics,
  metadata
}
```

Properties:

- no repository/file mutation;
- no AIWF/Ticket types;
- no requirement to execute the generated repository source in-process;
- reuse existing text-compiler prompt execution, critique and bounded recovery;
- caller remains responsible for language/project validation and project tests.

The exact API should be the **smallest extension** that supports exact replacement + new-file synthesis. Do not generalize into an “artifact compiler”.

### Why this is safer

Repository source is verified in its actual repository context by:

- ChangeEngine preview/language tooling;
- project typecheck/build;
- relevant tests/TestNodes;
- independent acceptance.

An isolated generated unit test inside text-compiler cannot substitute for those.

## 7. Generated-code execution boundary

There are now two different text-compiler uses and they must stay distinct:

### Repository source authoring

`compileSource` produces source text. It does **not** need to execute that source in AIWF's process.

Repository verification happens after safe mutation in the real project context.

### Ephemeral analytical composition

The J2.4 agency path may compile an executable helper/codelet.

Generated helper execution and dynamic verification must use the existing ToolContext execution authority/sandbox. Never execute generated code in-process when that would bypass read-only/cancellation boundaries.

If text-compiler currently lacks an injectable execution/probe boundary, add one minimal hook there rather than forking its verification pipeline in AIWF.

One executor/sandbox remains canonical.

## 8. Ticket.resolve target design

`resolve_ticket` remains the high-level public MCP operation.

Do **not** expose `write_code` publicly in the first implementation. External agents should still delegate the Ticket instead of reconstructing AIWF's internal implementation choreography.

### Exact target

Current:

```text
Ticket.resolve
 -> direct asker.json
 -> ExactImplementationSchema
 -> replace_symbol
```

Target:

```text
Ticket.resolve
 -> activate software-implementation skill
 -> write_code(exact target + Ticket intent/constraints)
 -> ChangeEngine
 -> tests / acceptance
```

Delete the duplicate direct source-synthesis path once parity is proven.

### Non-exact / multi-step work

Current implementation Actor may navigate and send arbitrary generated replacement source directly through `preview_change/apply_change`.

Target Actor tool surface:

- inspection/navigation tools;
- `write_code` for any AIWF-generated replacement/new **program source**;
- deterministic mutation tools for rename/refactor/source-actions;
- bounded generic change tools may remain for non-source configuration/documentation;
- no generic route that lets the Actor bypass `write_code` by stuffing AIWF-generated program source into `replace_symbol/create_file/replace_text`.

Whether a file is program source comes from existing file/index evidence and language metadata, never prompt keywords.

The Actor remains useful for finding targets and ordering multiple changes. It stops being an alternate code generator.

### Repair

A failed test or acceptance check becomes `feedback` to a subsequent bounded `write_code` invocation against fresh source.

Do not switch back to direct ad-hoc source generation on repair.

## 9. General Actor integration

The general agency plan keeps two separate compiler semantics:

```text
ephemeral computation over explicit evidence
  -> compile/run helper

repository source implementation
  -> software-implementation skill + write_code
```

System-1 tactical advice must distinguish them. “Compile” is not a synonym for “modify the repository”.

Suggested tactical means become:

```text
direct
capability
skill
compile-helper
write-code
environment
external-knowledge
```

This remains advisory. The Actor may choose another route.

A coding request with unclear target should normally:

```text
understand goal
 -> activate software-implementation skill
 -> inspect/navigate
 -> establish exact target
 -> write_code
 -> verify
```

A ranking/aggregation question should not invoke repository code writing merely because text-compiler is involved.

## 10. Public/internal surfaces

### Keep public

- `resolve_ticket` remains the normal MCP implementation entrypoint.
- existing precise change primitives remain public for deliberate expert/manual use.

### Keep internal initially

- `write_code` is registered in AIWF's internal ToolRegistry so Ticket.resolve and the local Actor can use/discover it.
- it is **not** added to `PUBLIC_MCP_TOOL_NAMES` until a concrete external actor journey demonstrates why bypassing artifact delegation is useful.

This preserves J5.1 rather than encouraging external agents to rebuild the resolver flow.

---

## 11. Obsolete paths after migration

After acceptance, audit and remove/subordinate duplicate source producers:

- direct `ExactImplementationSchema` LLM source synthesis inside Ticket.resolve;
- resolver Actor ability to author arbitrary replacement/new source through generic change tools;
- Actor-authored `sourceCode/testSourceCode` as the preferred self-extension path in `compile_codelet`;
- persisted one-off codelets where ephemeral text-compiler composition replaces them.

Do not delete `apply_block_patch` or deterministic ChangeEngine operations merely because they share a file with old compiler tools.

Delete only after usage search + tests prove the path is obsolete.

## 12. Acceptance

### Mechanism gates

1. Exact-symbol `write_code` uses text-compiler source synthesis and ChangeEngine apply; no direct `asker.json` source producer.
2. Exact-range/import-block and new-file writes follow the same canonical path.
3. Deterministic rename/refactor does not call text-compiler.
4. Dirty-target/lease/abort protections remain effective.
5. text-compiler/source synthesis failure produces a concrete blocker; no hidden direct-LLM fallback.
6. Missing software skill does not bypass hard safety.
7. Generated source/examples are never recorded as project evidence before mutation.
8. Aggregate metrics store hashes/counters, not generated source.

### Journey gates

#### J3.4 exact implementation
A realistic Ticket with one exact method target is resolved through `write_code`, tests pass, acceptance passes, receipt is current.

#### J3.1 multi-step implementation
A realistic Ticket requires navigation and at least two grounded source changes. The Actor discovers targets and invokes `write_code` for generated source; it does not hand-author source through generic change tools.

#### J3.2 repair
First implementation fails a relevant test. Fresh failure evidence goes back through `write_code`; bounded repair succeeds or reports a concrete blocker.

#### Deterministic control
A pure symbol rename is completed through existing deterministic rename machinery without invoking source synthesis.

#### MCP delegation
An external MCP agent calls `resolve_ticket`; the internal trace proves canonical code writing without the external agent needing `write_code` or patch choreography.

### Anti-bypass assertion

In the resolver implementation Actor, production traces/tests must prove that AIWF-generated **program source** for `replace_symbol`, source-file `replace_text`, source-file `create_file` and equivalent generative changes cannot be authored directly outside `write_code`. Non-source configuration/documentation changes are not forced through a programming source compiler.

---

## 13. Success criteria

Complete only when:

- one canonical AIWF source producer exists for generative repository code;
- it is backed by text-compiler rather than another ad-hoc prompt;
- software-implementation know-how is a concise built-in skill;
- Ticket.resolve uses the writer internally;
- multi-target Actors navigate/orchestrate but do not become competing code generators;
- deterministic refactors remain deterministic;
- mutation stays exclusively under CausalChangeEngine;
- real project tests/TestNodes + acceptance remain the proof boundary;
- J3.1/J3.2/J3.4/J5.1 live journeys pass;
- the general agency plan distinguishes ephemeral helper compilation from repository code writing;
- duplicate old source-producing paths are removed after proof;
- no new planner, manager, repository, registry, workflow engine or branch forest is introduced.

The intended architecture is simple:

> **Actor decides. Skill guides. Text-compiler writes. ChangeEngine mutates. Tests and acceptance prove.**
