# Dharmax-way

**The governing, test-first (TDD) method for defining and delivering correct product behavior**, implemented by [AI-Workflow](ai-workflow.md) and governed in engineering by the [Prime Directive](prime-directive.md). The developer owns intended product behavior and its approval; AI helps discover, propose, implement and verify it, but cannot approve its own product definition.

The default, adaptable system structure is defined separately in [Dharmax Architecture](dharmax-architecture.md). It informs project architecture without prescribing unnecessary components.

## Normal US-driven cycle

1. **Ground the work in the mandatory Product charter.** Review downstream Aspects, Features, Epics and USs against the developer-approved charter. Material conflict, ambiguity or drift must produce a specific warning and receive the developer's explicit answer before the definition is considered aligned/approved. Do not manufacture the missing charter.
2. **Define and approve the US.** Resolve its Actor, Intent, Initial State, Action and complete **Expected Result**, including relevant Feature/Aspect context. Reuse/revise existing canonical definitions.
3. **Generate and review the executable US acceptance test first.** It is derived from the approved effective US, not copied from the implementation or based on an AI-invented oracle. One cohesive file owns that episode and its meaningful scenarios. Before implementation starts, a materialized test may be skipped; an uncreated test is uncovered, not skipped.
4. **Establish the actual baseline when work begins.** Activate and run the real US test. Missing new behavior normally fails for the expected product reason (red). Existing behavior may already pass; provider/fixture/infrastructure failure is not expected red. Never manufacture a historical failure.
5. **Resolve through the governing resolution Ticket.** Establish/reconcile the Ticket that owns making the actual US test pass; it may exist before the baseline run to govern the work. Investigate enough to identify the actual unmet obligations.
6. **Prefer a full-flow skeleton when multiple components must cooperate.** Connect the real path, implementing actual functionality wherever practical, and using *temporary* internal stubs/mocks at genuine boundaries where necessary. Prove the connected path with a **separate skeleton test**. Its pass proves wiring/cooperation, **not US acceptance**: the original acceptance test is unchanged and its missing behavior remains red/unverified. If an implementation stub accidentally makes the acceptance test green, that run is not valid proof. No skeleton is necessary for a trivial direct change.
7. **Track each temporary internal stub immediately.** Automatically create/reconcile **one coding Ticket per stub**, identifying its location, missing real behavior and replacement/removal obligation. Reuse an existing Ticket for the same stub rather than duplicate it. Additional coding Tickets are derived only where genuinely useful. Controlled external test doubles are different from placeholders for missing internal functionality.
8. **Replace the stubs and implement the work.** Each coding Ticket makes its stub real and removes the placeholder. The [Prime Directive](prime-directive.md) governs the entire touched scope: **Concepts → Architecture → execution Flow → Implementation**; reuse actual component boundaries rather than invent mock-oriented architecture. Rerun skeleton and acceptance tests as appropriate.
9. **Prove the outcome.** The unchanged genuine US test passes *without internal placeholders*; all stub obligations are closed, necessary specialist tests pass, and independent **current** verification establishes the product behavior. Skeleton green, a completed coding Ticket or a graph link alone cannot prove US satisfaction.

This is a preferred strategy for multi-component work, **not** a mandatory collection of ceremonies or records for every change. Revisit the accepted test if intended behavior legitimately changes; do not weaken it to fit a stub. A bug generally belongs to its existing Story, while justified technical-only maintenance can use a direct Ticket without an invented US. See [the detailed design](../../plans/AIWF-DHARMAX-WAY-DESIGN.md).
