# Test

An executable check of actual behavior or a necessary engineering invariant. **AIWF testing is US-driven by default, almost exclusively.** Derive the genuine product acceptance test **before implementation** from an accepted, complete [User/Actor Story](user-story.md): its actual Initial State, Actor Action and **Expected Result**, exercised through a public interface. The accepted effective US (including its inherited Epic content, applicable Aspects and [charter-alignment decisions](product.md)), not a stub or existing implementation, determines the oracle. Passing a test cannot cure an unanswered charter warning.

**Organize acceptance tests by US: normally one cohesive executable test file per accepted US.** If that file becomes unwieldy, split it into **multiple files belonging to the same US**, not arbitrary technical test groupings. Cover ordinary, conditional, non-pristine, regression and relevant failure/safety scenarios under that Story. A meaningful [sub-US](sub-user-story.md) is itself a US. Each acceptance-test file must identify its governing official US, rather than merely sharing a naming convention.

## Separate full-flow skeleton test

For multi-component work, a separate **skeleton test** may prove the complete path is connected while deliberately temporary internal stubs/mocks provide missing functionality. Real components are preferred wherever practical. **Skeleton green means wired, not implemented or accepted.** The real US test is *not* changed, mocked into passing or replaced. It remains active/red for genuinely unmet behavior; if temporary placeholders misleadingly make it report green, that run is not valid acceptance. The skeleton test is an implementation aid, **not** another US or competing acceptance oracle.

Each temporary internal implementation stub automatically has **one coding Ticket** to replace it with real behavior and remove the placeholder; reconcile an existing Ticket for that same stub, without duplication. Controlled test doubles for genuinely external dependencies are distinct from unfinished internal functionality. Do not create artificial production interfaces purely to facilitate mocking. Full-flow-first is preferred when several components must cooperate, not mandatory for trivial changes.

**A test with no related official US should be exceptional.** Focused technical/unit tests for demonstrably complex/critical invariants (e.g. atomic batches, leases, parsers) are justified only with a documented engineering reason and a clear relation to the protected behavior; they supplement, never substitute for, Story proof. Shared fixtures/helpers do not become new Story suites.

**Legacy migration:** Existing tests are evidence of implementation behavior, *not* authority for intended behavior. For each legacy suite, first locate its governing accepted US; if none exists and the behavior is genuinely part of the product, draft a complete US using the approved fields, review/accept it through the canonical Product workflow, **then** derive or reorganize its tests. Do not invent a US solely to legitimize a historical test, silently approve a retrospective requirement, delete useful regression coverage before replacement, or mass-rename files without behavioral mapping.

At work start, establish the actual US-test baseline (normally expected red for missing behavior, but potentially already green for implemented behavior); a wrong-reason failure is not expected red. Rerun the same genuine test after implementation and verify current results independently. A test definition, Test graph node, test run and current proof are distinct; do not infer success from graph links, stale pass flags, Ticket lanes or skipped/unavailable tests. Never invent historical red. See [the governing testing design](../../plans/AIWF-DHARMAX-WAY-DESIGN.md#4-testing-stories-are-the-measure).
