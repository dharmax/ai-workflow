# Feature

An **enduring responsibility/functionality of the product**. Top-level Features form the Product manifest's feature map; narrower Features are legitimate when they have distinct product meaning, not merely because a delivery task exists.

The minimum meaningful definition is **stable ID, Title and Responsibility** (what the product undertakes to do). Additional detail may include intended outcomes, scope/boundaries, feature-specific behavioral rules and existing priority/acceptance/completeness metadata where useful—not compulsory form-filling. The concise manifest entry and detailed Feature definition refer to the **same identity and revision**.

A Feature may enable concrete [USs](user-story.md) and be governed by reusable [Aspects](aspect.md). A Feature says *what the product is responsible for*; a US defines an episode of use; an [Epic](epic.md) groups delivery; a [Ticket](ticket.md) is bounded work. None should be mechanically created solely to satisfy an artificial hierarchy.

Developer acceptance of a Feature's definition is not evidence that it has been implemented or verified. See the [agreed Feature contract](../../plans/AIWF-S5-POSTCONDITION-DESIGN.md#321-product-manifest-and-feature-definitions--2026-10-17-agreement).
