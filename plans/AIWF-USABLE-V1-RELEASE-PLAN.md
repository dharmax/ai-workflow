## 1. Decisions and definition of done

These decisions are binding for the proposed v1 release; approving this plan adopts them. They do not replace any independently required verifier or falsely authorize a Done transition.

1. **Bug ships in v1, full stop.** Bug is a first-class **public artifact and operation family**, canonically a typed variant of existing `Ticket`, sharing identity, state, claim, verifier and graph rather than acquiring a second database/queue. Implement all of §2, not merely a `[BUG]` label or title heuristic. `TKT-BUG-TYPE-LANE`/PC3 is a required implementation owner.
2. **D1:** External AI agents have Product *proposal/read*, not self-approval. Apply only with the exact host/human-reviewed current fingerprint. Local host review uses current context. If a host cannot review, respond with inert `review_required`. No fake consent via model `decision:'accept'`, `--yes` or ordinary `project-write`; explicit bounded delegation is deferred.
3. **Actual operability, not just a correct graph:** Normal CLI, shell and available Workspace must let a person inspect, create, edit, relate, review, process, report Bug, select work, see tests/proof and resolve without hand-authored internal JSON/raw database calls. The selected typed MCP operations must describe the same canonical semantics. Use existing Commander/domain owners, not another command framework. A capability is advertised only where genuinely supported.
4. **One release-focused Kanban:** `In Progress` means actually selected work; at most one primary executing Ticket. `Todo` is a short ready queue (target 1–3). `Blocked` shows relevant *current* obstacles; nonpriority work and historical waiting items go to `Backlog` with reason/evidence intact. `Done` is never a tidy-up operation. The board is a canonical projection, not a second workflow owner.
5. **One demonstrable product journey with two branches:** in one other tracked repository: (A) add an enduring Feature and implement a genuinely missing public behavior; (B) report a Bug against existing behavior and correct it **in place**. Both end with AIWF's own resolver, actual tests, material obligations and independent current verification. Codex/AGY repairs AIWF but must not impersonate AIWF doing the target-project work.

### What success looks like, in order

`init / doctor → optional Product/Manifest → Goal/Concept/Feature responsibility → explicit Aspect/Rule applicability → Flow when useful + complete accepted User/Actor Story → preview/review/accepted revision → reconcile Epic/Ticket and test → materialized skipped Story test → activate/observed expected red → investigate/claim → guarded code edit by AIWF → observed green + relevant specialist/Aspect/Rule checks → independent verifier + one current receipt/Done → claim release → restart/inspect`.

Then `bug report → triage → correlate with existing Story/Feature/source → reproduce or mark unknown → reviewed in-place correction and test basis → native resolve → current proof/Done`; previous historical receipt remains historical if a revision invalidates its basis. **No mandatory Flow for every Story, Feature per Ticket, Story for a pure technical repair, or fictitious preimplementation red for previously working code.**

## 2. Mandatory first-class Bug contract (PC3) — release gate, not backlog polish

**Historical source gap before I1 (typed Bug operations are now implemented; native external completion remains unverified):** `Ticket`/`TicketData` lack typed `kind` and defect data; `recommend_next_task` guesses bugs from words in IDs/titles; `kanban.md` groups by lanes and does not show Bug type. The following retained contract still governs independent end-to-end qualification; do not restart the implemented type/operation work.

### Canonical model and behavior

- Use **the existing Ticket entity/ID/relations/leases/lanes/verifier** with `kind?: 'task'|'bug'`; legacy missing kind reads `task`, no migration by name. A Bug is first-class from the user's perspective, **not a separate persistence schema, fake Feature, Lesson, or text prefix**. Explicit same-ID reclassification is a reviewed authored operation preserving history; no accidental conversion of historical tickets, no title-based classification.
- Strict optional `defect` fields from Product Operability design §3.4: `reproduction`, `expected`, `actual`, `severity` (`critical|high|medium|low`), `impact`, `environment`, `evidence[]`. Unknown stays unknown. Partial reports are allowed and discoverable, but cannot be silently promoted to implementation-ready without reproducible behavior or an explicitly bounded diagnostic acceptance contract. Evidence URLs/paths do not automatically certify results.
- Human operations must actually work: **report/new, list/filter/find, show, edit/complete report, assess/triage readiness, link existing artifacts, inspect dependencies and related proof, prioritize, claim/start, block/reopen/cancel, resolve, show verification history**. Provide `bug`, `bugs`, `work bug` and typed artifact/MCP support for operations v1 advertises, plus practical Workspace entry/view/edit. Existing Ticket readers also show Bugs with their real kind; `bug show` does not accept a task. A failed `resolve` releases the lease and records a precise blocker, not Done.
- Ground a bug in existing Product meaning: use `addresses` for the existing Story where appropriate; `implements` only if genuinely implementing the existing Feature; use the existing typed `targets`/`modifies` source/Module relations. Check for equivalent current Bugs/Tickets and update/link rather than create duplicate active defect work. Report observed failing behavior and exact source/test basis. For a bug requiring a meaning change, review/version the **same Feature/Story** and show impact; ordinary repair does not redefine Product meaning automatically.
- `next` and readiness: exclude Backlog, Blocked, Done, **active foreign claims**, and unsatisfied/missing prerequisites as specified by current design; expired leases are handled/recovered by the existing lease owner, not silently treated as a permanent disqualification. Favor eligible own lease; otherwise current eligible In Progress, then Todo. Sort explicit priority P0→P3; within equal priority, Bugs with known severity precede tasks and Bugs rank critical→low→unknown, followed by stable creation/ID. No words-in-title ranking and no model-based hidden ordering. Start rechecks the graph/claim and activates applicable S5 Story test *before* implementation. Never set Done through a generic lane setter.
- Kanban: keep the five existing lanes. Render a visible, non-destructive **Type: Bug / severity / priority** marker within each Bug card, not a new Bug lane. The existing Obsidian importer must round-trip without copying the marker into the canonical title or overwriting defect fields. `bugs`/filtered Bug view derives from the same data; no independently editable second board. Distinguish typed outstanding Bug counts from source `Lesson`/TODO/notes in module-health presentation.

### Bug acceptance in an actual external project

`report partial → inspect unknowns → complete reproducible defect → see Bug on Kanban and via CLI/shell/typed read → attach existing Story/Feature and actual test/source → compare duplicate/pre-existing work → ranked eligible next → start/reproduce actual red → review guarded fix preserving original identities → run green and exception/Aspect/Rule checks → independent current verification → canonical Done/restart`. Include negative checks: partial report not implementation-ready, fake red rejected, title `fix...` is still task unless classified, invalid severity, unmet dependency, foreign claimant, rejected/canceled/reopened proof and duplicate/reclassification semantics.

**Gate:** A user can use Bug as a native artifact through the whole path. Showing `[BUG]` without correct authoring, behavior and proof is a FAIL.

## 6. Anti-drift execution rules and reporting

1. **Make a release gap register, not another architecture audit:** at I1 entry one page: `required user action → existing source owner + canonical Ticket → current proven behavior → one missing public behavior → iteration`. No new Ticket for every step; use existing IDs, accept/update only real prerequisites. Do not reopen/repair a previously delivered component without an observed failing release scenario.
2. **Use the same two target-project Stories throughout all three rounds.** No moving goalposts, fake direct-DB setup, toy internal-only passing cases or proliferation of fixtures. The target is an independently initialized, tracked application with an actual public interface and test runner; the release trace records its initial state and edit history.
3. **One owner at a time.** Complete the smallest coherent cross-owner vertical slice; keep tests real, use installed first-party components instead of shadow abstractions, audit full changed methods and immediate callers, preserve unrelated work. No branch forest, destructive reset/force push, unrelated sibling source changes or speculative refactor.
4. **Stop-go only on observed evidence.** Each iteration ends with actual public behavior, first residual failure, linked canonical owner/ID, test pass/fail/skips including pristine and provider paths, current claim/review/proof outcome, source/dep hashes and pushed remote SHA. A stage review may authorize the next round; it may not mint a false Test receipt. If I1 or I2 fails, next budget fixes the failure, not a new feature wishlist.
5. **Defer honestly:** future seed retains help-completion, compositional queries, full outline and log deliberation. Minor UX defects go to their existing Backlog owner. A major navigation/triage defect is required v1 work **only if** it obstructs the native external-project journey; no generic log-analysis design has been approved.
