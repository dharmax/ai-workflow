## 0. Architecture and authority

**The public API is one `CommandRegistry` plus four transport projections, not four APIs built domain by domain.** Rename the existing exported `ToolRegistry` **class** to `CommandRegistry` and migrate its imports, references and tests. Its instance should use the explicit name `commandRegistry` where practical; avoid retaining obsolete public aliases as a permanent compatibility layer. The existing `src/tools/registry.ts` is the starting implementation—its file location may remain unchanged to minimize churn.

**Vocabulary boundary:** In AIWF, *tool* has a distinct meaning (e.g. Actor/internal capability and MCP protocol tool). A **command** is the public resource/action operation with typed input/output, human help and eligibility across transports. Existing real internal `ToolDefinition`/tool handlers are execution providers, not automatically public commands. Define/use a lean `CommandDefinition` metadata contract as part of the SAME `CommandRegistry` (e.g. optional public command descriptors linked to underlying registered handlers); do not duplicate handlers, schemas or create an independent registry. Keep `ToolDefinition`/`ToolContext` terminology only for genuine internal-tool semantics when applicable; do not blindly rename MCP protocol concepts or all existing tool files.

One supported public **command** declares its `topic[:subtopic] action`, description, exact owner/schema, CLI positional/option presentation, eligibility, authority and only necessary transport hints. Commands are not synonyms for tools; multiple public commands can reuse one internal tool/domain owner when their action schemas require it. Generate or derive:

- CLI Commander command tree, `--help` and scoped help.
- Shell UI completion/facilitation using the same grammar and `@dharmax/shell-ui` interaction.
- MCP advertised semantic families and strict native JSON input schemas.
- **Dynamic REST routes** `/api/v1/topic[/subtopic][/{id}][/{action}]`, HTTP verb mapping and OpenAPI 3.1, at startup from eligible verified public descriptors. Reuse `src/workspace/server.ts`; it is the HTTP host, not a separate API owner.

**Visibility is explicit opt-in.** Existing registry entries do not automatically become public. Internal-only tools, unsafe writers, unsupported future actions and actions lacking required trusted approval are never advertised or routable. There is no external `args:any` bag, open-ended `action:string` list, manual duplicate `PUBLIC_MCP_TOOL_NAMES` source of truth, independent REST catalog, or handwritten help table.

Domain truth, accepted Product intent, RuleStore, S2/host review, Test owner, Causal Change Engine, Semantika, and the Prime Directive remain authoritative; transport metadata grants **no new permissions**.

## 2. Pass A — rename, canonical command registration and automatic externalization

**Complete the current Codex Stage 0 + S1 assignment here; do not throw away correct work in progress.** The purpose is **one declaration → working outputs across all four interfaces**, not implementing eight arbitrary operations with bespoke adapters.

1. **Rename `ToolRegistry` → `CommandRegistry`** in production code, update imports/types and tests, and establish `commandRegistry` as the main singleton name where appropriate. Preserve the behavior of internal Actor tools and existing MCP transports while migrating. The registry represents command discovery/dispatch metadata plus references to existing internal tools/domain owners; it must not redefine the special meaning of `tool`.
2. Add the **smallest** `CommandDefinition` public metadata/adapter in this same registry. Canonical identity is `topic[:subtopic] action`, with typed schema, help/argument presentation, transport eligibility, authorization and a referenced existing domain handler. One internal tool may back multiple commands with distinct schema restrictions. Never expose a private tool merely because it is registered. Keep actual permissions, review and state management in the domain owner. Do not build a replacement dispatcher or duplicate parsers.
3. Define deterministic, idempotent command registration/bootstrap before constructing **any** public projection. Confirm no circular import or partially initialized registry; build Commander commands **and `--help`** (global, topic, action) from the same completed eligible-command snapshot. Shell UI uses the same command tree and existing completion, facilitation, renderer, review and TTY lifecycle. Invalid explicit command never falls through to the Actor.
4. Generate public MCP schemas and tool discovery from the same metadata, with intentional semantic family grouping and compact discovery. Remove hard-coded public lists *only when parity/compatibility is proven*. Do not publish internal primitives by default.
5. Generate REST routes and OpenAPI **dynamically from eligible registered operations** using the existing Bun Workspace server. Standard `list/show/create/update/delete` map to GET/GET/POST/PATCH/DELETE; specialist actions retain their name and trusted method declaration. Registration compiles to a checked route table: genuine ambiguous collisions fail closed, while explicitly disjoint shapes (e.g. graph-link GET `list` vs `show`, distinguished by an exact triple) dispatch deterministically. No route handwritten for each operation. REST resource name = topic/subtopic **exactly**, no new pluralization. Preserve legacy Workspace UI paths through thin adapters until browser callers are safely migrated; page/session/assets are transport routes, not catalog operations.
6. Reuse existing runtime schemas, typed JSON, exact identity, revision and provenance semantics across surfaces. `--data-json`, `--data-file FILE|-`, `--value-json`, `--payload-json` apply **only** to operations accepting those values; `--json` outputs machine data. Reject malformed/duplicate-key/unknown/protected fields, source collisions and unauthorized transport changes.
7. Prove **real representative operations**: `ticket show/status`, `graph:predicate list/check`, `graph:link list/show` (and bounded read-only `ticket investigate` if already supported). Do not implement graph mutations or rewrite the resolver merely for this pass. A fixture registration should automatically affect CLI help/completion, MCP discovery, REST routing **and generated OpenAPI**, with appropriate channel eligibility; disablement removes it everywhere.

**Gate A:** the `CommandRegistry` rename is complete (no stale active `ToolRegistry` references); internal tool execution remains intact; one canonical command registration path, zero required per-operation handwritten command/MCP/REST/help entries. ## 4. Non-negotiable execution discipline

- Before implementing, inspect the actual local state and current code: source behavior beats stale GitHub reports. Existing EXT-SURFACE tickets remain the only execution backlog; do not create a second issue system.
- Solve root causes; **rename/refine the existing registry, don't create another** command bus/registry, DB, reviewer, HTTP server, UI renderer or separate transport ontologies. Review legacy `ToolRegistry` references after the rename; preserve names `tool` only for true internal/protocol tools.
- Public registration/availability, schemas, help, runtime MCP discovery, REST routes and generated OpenAPI are checked by **cold-start, repeated-initialization and add/remove operation** tests. All surfaces consume the same completed snapshot; no circular/partial initialization. Reject collisions and unrepresentable schemas; a disabled operation cannot be invoked by direct URL/tool name.
- No model self-approval: caller-controlled JSON, `--yes`, Workspace token, `decision:'accept'`, MCP or REST request do not themselves grant developer acceptance. Existing governance stays enforced at the owner.
- Long-running operations stream progress/cancel only where real execution lifecycle supports them. Do not invent durable jobs, routes or evidence.
- Report exact verified surface coverage, tests, source and remote commit hashes, blockers, cleanup. Push by normal fast-forward only; delete the docs branch only after latest files are verified on upstream master.

## 5. Implementation notes and exit checks

- **What exactly gets renamed:** the `ToolRegistry` class and public command-registry references; preferably its exported instance (`registry` → `commandRegistry`) where safe. Update `src/tools/registry.ts`, `src/tools/index.ts`, `src/tools/surface.ts` and their real importers. Existing `ToolDefinition` and MCP `tools/list` remain legitimate *tool* concepts unless a concrete usage is actually a command; public metadata is `CommandDefinition`. No blind global search-and-replace of every word `tool`.
- **Command registration must own** public names, action set, descriptions, arguments/options, typed validation, result shape, eligible transports, trusted-authority requirements, and allowed HTTP method. The underlying domain owner remains responsible for execution and authorization. Public support may be explicitly false or channel-specific; public metadata does not grant execution.
- **Generated outputs:** Commander/`--help` (root/topic/action), shell-ui autocomplete/facilitation, MCP tool advertisement via explicit mapping, dynamically generated REST routes and OpenAPI. One command addition/update/removal must not require separately editing five declaration tables.
- **Compatibility:** existing user-facing CLI and Workspace/MCP integrations remain functional while migrated. Legacy alias wrappers are temporary and cannot circumvent owner validation, expose blocked commands or serve as competing API specs.
- **Security:** duplicate command IDs, ambiguous route/input overlaps, unsupported Zod→JSON Schema conversions, missing HTTP semantics or missing trusted approval must **fail closed**, with clear errors. A legitimate same-method/path list/show pair must use a schema-proven discriminator (e.g. complete graph triple); never silently select by handler order. Disabled/public-ineligible commands cannot be invoked directly by REST URL, CLI string or MCP call.
- **Finish state:** Pass A provides working registry-driven generators; Pass B integrates existing useful domain capabilities and essential safety corrections. Internal improvements to `ticket resolve` or source `xray` are separate product work.
