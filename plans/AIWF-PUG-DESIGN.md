# AIWF Product Usability Gate (PUG) — Design

**Status:** Proposed for developer approval, not an implementation authorization. **Basis:** published `dharmax/ai-workflow` master `ddff7b5c7313de1d30bae56c79cc47826051a15c` (16 October 2026), canonical Dharmax-way design/plan and S1–S5 evidence. Recheck local HEAD, working tree and canonical DB before work. **Placement:** mandatory checkpoint after S5 and before S6. S6's governed implementation/resolution scope is unchanged.

## 1. Product outcome and non-negotiable test

A developer can open a fresh or existing project, state what the product is for, define/refine Goals, Concepts, journeys and reusable concerns, inspect module purposes, manage all valid relationships, report and work a defect, plan and trace work, and understand actual verification without using `eval`, hand-authored JSON, Markdown projection editing, or direct DB access. CLI works noninteractively; shell and Workspace provide human review. External agents can use appropriately selected public operations. All adapters share canonical validation, version checks and mutation ownership.

Product intent belongs to the developer. No AI or critic auto-accepts a product decision. No UX convenience bypasses the S2 reviewed Product mutation path, S4 identity reconciliation, S5 test freshness, lease/Done verification or Gate 5 governance. A pure technical task requires no manufactured Feature/Story. A reported defect does not automatically authorize implementation or completion.

## 2. Source-grounded inventory (do not mistake internal capability for a usable public workflow)

- `Goal`, `Concept`, `Flow`, `Feature`, `UserStory`, `Aspect`, `Epic`, `Ticket`, `ModuleNode`, `TestNode`, `Decision` exist. `ModuleNode` has `path`, `body` and completeness target; there is no demonstrated first-class product charter or dedicated module goal definition.
- `aiwf init` indexes/scaffolds and exports projections; it does not capture product intent. CLI reads Epics, Features, Stories and Tickets, not the full intent inventory. `src/workspace/client.js` edits Feature/Aspect/UserStory; other artifacts are largely view-only or advanced JSON.
- `src/product/mutation.ts` owns the allowed endpoint/predicate triples and reviewed Product mutations. `link_product`/`unlink_product` exist as registered tools; a general human CLI is absent. Workspace has a static predicate dropdown rather than constrained choices derived from the relation contract.
- Tickets have no explicit defect kind. `recommend_next_task` currently uses `id/title.includes('bug'|'fix')`, a false heuristic, and should be audited for actual priority semantics.
- `src/tools/surface.ts` intentionally selects public MCP operations; exposing the entire internal registry is not the solution.
- CLI dispatch is case-sensitive; `artifactCommand` normalizes some verbs, not the complete surface. Human entity lookup's case behavior must be tested separately. Canonical IDs, source paths and file/test identity must remain exact.
- S4 manual proposal and S5 runnable Story test exist. The model-backed S4 proposal route remains unqualified because of provider authentication; do not retry to justify this deterministic UX gate.

Before editing, inventory every artifact and action against all surfaces: list/search, get, create, revise, deactivate/delete, relation discovery/add/remove, impact, review/approval, work status, proof. Inventory existing CLI, shell, Workspace, public MCP and registry owners; mark each **works**, **exists internally but inaccessible**, **broken**, **deliberately internal**, or **not applicable**. The matrix is an acceptance artifact, not permission to expose every primitive publicly.

## 3. Canonical meaning: keep the layers distinct

| Item | What it owns | What it must not become |
| --- | --- | --- |
| Project/Product definition | One project-level charter: product identity, purpose, intended actors, outcomes/bounds and references to Goals/Concepts. | A second database, duplicated Goals, or a compulsory ceremony for a maintenance-only repository. |
| Goal | Desired outcome; explicit product-wide or module-scoped applicability. | A Ticket or copied module description. |
| Concept | Domain/product meaning and governing design idea. | A Rule copied onto each consumer. |
| Flow (product) | A significant actor journey; serves Goal, contains Stories as appropriate. | Mandatory parent for every Story; engineering call flow. |
| Story | Actor, Intent, Initial State, Action, observable Result, relevant Exceptions/Bounds. | Feature specification or a title-only acceptance oracle. |
| Feature | Reusable capability enabling one or more Stories. | Story container (legacy Feature `contains` Story remains readable but cannot be newly authored). |
| Aspect | One authoritative cross-cutting obligation with explicit scope and documented inheritance. | Copy-pasted policy or automatically successful proof. |
| Module | Actual architecture/code owner, purpose, responsibilities, bounds and applicable product intent. | Another Feature/Goal type or inferred ownership with no evidence. |
| Epic | Organized delivery targeting established intent and containing Tickets. | Rival product definition. |
| Ticket / Bug | Bounded work and lifecycle; Bug is a typed defect on the existing Ticket execution substrate. | Separate bug board/runner or title-matching classification. |
| Test, Decision, Rule, File/Symbol | Executable evidence, accepted decisions, effective engineering governance and source anchors respectively. | Graph edges as substitute for public execution. |

### Project and module intention, without inventing competing authorities

Add the **smallest canonical product charter** after inspecting whether the current store already has a suitable singleton metadata owner. A charter is one versioned project-level record, not prose repeated across Goals: name/identity, purpose, primary actors/users, boundaries/non-goals, and explicit referenced Goals/Concepts. A repository may remain `undefined`/needs-definition while pure technical work proceeds. `aiwf init` stays a safe, non-generative indexing operation; a separate `aiwf product` read/define/revise entrypoint, offered as the next step after init, handles reviewed definition. Existing repositories must not acquire fabricated charters or accepted Goals on migration.

For module intention, reuse canonical `ModuleNode` with its real path/identity and reviewed description; expose a compact purpose/responsibilities/bounds view, with explicit Goal/Concept/Aspect links. Extend the central relation contract only where semantically required and tested, e.g. `Module serves Goal` and `Concept governs Module`. An architectural module can serve multiple Goals and a Goal can span modules; do not force a rigid tree. A discovered/indexed module may have unknown purpose until reviewed. Do not infer code ownership or Aspect propagation through arbitrary links. Reuse `Ticket targets Module` and existing source graph where relevant. If a separate `Product` entity or module field is actually needed, document the precise missing owner and migrate in place; no parallel YAML/Markdown authority.

## 4. The human command contract

Use one thin CLI adapter over canonical public domain operations. Consistent singular/list/edit grammar for key artifacts; retain existing commands and avoid duplicate synonymous implementations. E.g. `aiwf goals`, `aiwf goal G`, `aiwf goal create ...`, `aiwf goal edit G ...`; same discoverable pattern for Concepts, Flows, Features, Stories, Aspects, Epics, Tickets and Modules, with specialized lifecycle commands for work/tests. Expose Idea/Decision/Rule inspection and appropriate existing management operations; do not force every source graph node into product CRUD. Every family must have complete help, examples, coherent errors, `--json` where useful, and deliberate non-applicability rather than silent omissions.

**Case semantics:** command keywords, subcommands, flags where applicable and human-readable enum inputs are case-insensitive. Human-facing entity ID lookup should accept a case-insensitive *unique* match but return/display the exact canonical ID. If case-folding collides, demand exact input; never select arbitrarily. Never lower-case persisted IDs, file paths, symbol names, quoted content, free text or source/test artifact identity. The executable filename itself follows host OS rules (`AIWF` may require an alias on case-sensitive Linux); do not claim otherwise.

**Relationships:** provide `aiwf relations [id] [--incoming|--outgoing|--all] [--predicate P] [--json]`, `aiwf relations allowed [source-kind] [target-kind]`, `aiwf link <source-id> <predicate> <target-id>`, `aiwf unlink ...`. Help/discovery, UI pickers and validation must derive from **one exported canonical relation definition**, not cloned string lists. Support all approved source/predicate/target combinations, correct direction and multiple links; distinguish typed ID collision, absent entity, invalid triple, already-present/absent link and cycle/semantic invariant. Display endpoint type and human title. Default mutation is a non-mutating diff; an explicit acceptance action applies the exact versioned preview/fingerprint via S2. Interactive shell/Workspace may offer confirmation, CLI remains noninteractive. For one-step CLI usage an explicit `--apply` may signal acceptance **only if** it uses the same freshly displayed preview, fingerprint and atomic Product apply, with stale conflict handling. Batch relationship edits use existing multi-mutation Product review rather than repeated partial writes. `aiwf graph` remains diagnostic traversal, not the relationship editor.

**Bugs:** first-class human type, not necessarily a new entity. Add explicit `workKind: task|bug` (name subject to source-contract audit) to existing Ticket; legacy Tickets default to task without name-based reclassification. Bug-specific reviewed fields: reproduction (initial conditions, steps/action), expected and actual observable results, impact/severity, affected product/version/environment if known, optional linked Story/Feature/Module/source and reproduction evidence. Severity and work priority remain independent. `aiwf bugs [lane|filters]`, `aiwf bug <id>`, `aiwf bug create`, `aiwf bug edit` and conversion/classification if explicitly reviewed; normal claim/move/resolve/verify/Done operate through Ticket machinery. `aiwf next` selects actual typed Bugs by documented severity/priority + prerequisites/leases, never title substring; do not quietly steal another agent's lease. Bug repair should establish real red reproduction where feasible, then governed green; inability to reproduce is identified, not manufactured. Avoid an obligatory Feature/Story for narrow technical defects, but use existing relevant Story/Aspect when present.

**Completeness of decisions:** include `help` and actual list/show/manage pathways for project charter, Goal, Concept, Flow, Story, Feature, Aspect, Module, Epic, Ticket/Bug, decisions/rules, relations, test status and verification; update/deprecation/delete paths must reveal dependencies/impact and require reviewed authorization. Do not add commands that pretend later S7 satisfaction or S8 portable restore is complete. Present `unknown`, `uncovered`, `stale`, `blocked` faithfully. Provide guided suggestions for unsupported operations and existing read-only artifacts.

## 5. Workspace / shell / MCP

- Workspace: add clear **Product / Architecture / Work / Verification** navigation without a heavyweight SPA. Product charter, Goal/Concept/Flow editors and existing Feature/Story/Aspect editors should be discoverable, searchable and keyboard usable. Architecture shows Modules with reviewed purpose and linked intent. Work shows Epic/Ticket/Bug creation, review and relationships. Verification shows actual Story status, never inferred Feature success. Relationship picker uses type-constrained canonical alternatives, in/out links and removal preview; no mandatory proposal JSON for routine edits. Full multi-entity proposal JSON remains an advanced route.
- CLI: never prompt by default; show actionable usage/errors, support human direct edits through the S2 review contract.
- Interactive shell: facilitate *missing* parameters and confirmation only; complete commands do not solicit input. Reuse command/parser/domain operations rather than parallel shell implementation.
- MCP: preserve deliberate narrow public selection, but expose the coherent product and work operations necessary for an external agent to perform the same approved journeys (including relevant read/review/apply and relation discovery). Do not leak `script_eval`, unguarded registry or generic DB mutations. JSON results include exact canonical IDs, statuses, versions and blocked/needs-input reasons.

## 6. Whole-product journeys that must be demonstrably usable

- **PUG-01 Fresh start:** init/index existing repository, inspect existing state; explicitly review/create charter, top Goal, Concept and Aspect; reopen with same identities. Declining onboarding leaves no fake product records and technical Ticket remains available.
- **PUG-02 Module context:** inspect indexed Module, define reviewed purpose/scope, link to relevant Goal/Concept/Aspect, query both directions; source/module identity preserved; no implicit inheritance from unrelated Epic target.
- **PUG-03 Product evolution:** define Flow, complete Story, Feature and relations; create/revise/reject via actual review; derive/reconcile existing Epic/Tickets and S4 Story test rather than duplicates.
- **PUG-04 Relationships:** enumerate every allowed triple from canonical contract; add/remove representative links from real CLI and Workspace; invalid type/direction, collision, stale preview and cancel cause no partial write; legacy Feature contains Story is readable/removable but cannot be newly authored.
- **PUG-05 Defect:** report bug on an existing Story/Feature, inspect from `bugs` and `bug`, link context, prioritize, recommend through `next`, reproduce test-first, use same Ticket state/evidence; title-only `fix` task not mistaken for Bug.
- **PUG-06 Human input:** keyword/subcommand case variations and unique case-folded IDs work; case-colliding IDs fail without selecting one; identifiers/source paths/free text retain original spelling; shell facilitates missing fields only.
- **PUG-07 Existing work:** reopen a prior project with legacy Tickets/Story links/projections, edit in place, preserve claims/Done/verification/Aspects, avoid fictional green or reclassification.
- **PUG-08 Surface parity:** same approved update inspected through CLI, shell, Workspace and selected MCP operation, same versions/relations/error semantics and no adapter-specific domain writes. At least one multi-entity review is canceled, one approved and one made stale in parallel.
- **PUG-09 Guardrails:** dependency block, invalid link, DB failure, unauthorized source change and dirty-file conflict cannot produce accepted work, partial canonical graph or fake verified result. Existing S1–S5/Gate5 regressions pass.
- **PUG-10 Realistic everyday use:** human completes the primary journey without `eval`, handcrafted request JSON, manual DB/projection changes or invoking internal tool names. Count required command/action steps and fix material friction before calling the gate complete.

Each journey records initial state, human action, actual public interface, observed persisted effect and negative test. Internal-only unit tests supplement but never replace these.

## 7. Explicit limits and acceptance

No S6 resolution-engine rewrite in PUG; do not add autonomous provider dependence to deterministic acceptance. No second database, command bus, generic new graph engine, shadow mutation path, fake `Bug` lifecycle, broad refactor, mass entity migration or premature S8 projection retirement. `aiwf eval` remains a useful advanced escape hatch, not the answer to missing product UX. S1–S5 behavior, provider limitation, Gate 5 status and Semantika dirty files remain truthfully preserved.

PUG is accepted only when the inventory/matrix has no unowned mandatory journey, a fresh and existing project both complete the real human paths, preserved/canonical state survives reopen, CLI/help and UI expose the same business meaning, selected MCP supports agent delegation, all negative safety checks and baseline regressions pass, and a pristine checkout contains every required implementation/test/fixture/help artifact. This acceptance **authorizes consideration of S6**, not execution or parent Ticket Done.
